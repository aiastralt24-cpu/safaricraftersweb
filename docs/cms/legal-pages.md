## Atomic draft application backend
Local migration 106 introduces `apply_legal_migration` and actor-scoped `get_legal_migration_result`. A batch covers one to three distinct legal routes with source hashes, explicit create/update targets, expected current revisions and candidate payloads. The transaction delegates writes to existing `save_draft`, preserving authorization, audit and revision semantics. No publish operation occurs. A failed item rolls back all draft writes and the receipt. Completed identical retries return original results; changing source/review digests or manifest under the same actor/site/request key is rejected.

Current create/edit authority is checked before receipt replay. Recovery reads require current view access to every result record and cannot reveal another actor's or website's receipt. Receipt tables expose no direct authenticated select grant. Source/review hashes bind retries; they are not themselves proof that a client supplied trusted legacy content. The forthcoming server review/API must reconstruct approved candidates from the controlled capture before calling this RPC. This is draft infrastructure, not a publication bypass or a complete migration interface.

## Authenticated migration review/apply/status API
`POST /api/cms/migrations/legal` now accepts `review`, `apply` and `status` commands. Review/apply select one to three unique legal routes with explicit record ID/current revision pairs, or null pairs for creation. The client cannot provide source text or candidate payloads. The server rebuilds candidates from the deployment-owned capture; build tests verify capture freshness against repository source. Review returns existing draft content alongside the candidate and a digest bound to website, selected target revisions, source content and migration version.

Before a new application, existing targets must be editable English page records at the exact selected route and current revision; creation requires current page-create authority. A concurrent change is still rejected transactionally by the database. Existing-path creation collisions remain database conflicts; select the existing record for updates. Completed retries first recover their actor-scoped receipt, then call the apply RPC with the exact original manifest to recheck authority and idempotency. They do not incorrectly reject the now-superseded pre-apply draft revision. Altered review inputs are rejected; missing/malformed/mismatched result receipts require status recovery rather than guessed success.

The endpoint uses the caller token only, rejects cross-origin requests and unknown command fields, and returns private no-store/noindex responses. Status does not claim absence of a completed receipt means an in-flight operation failed. No API path publishes content.

## Client review, application and reload recovery
The Pages workspace now includes **Import existing legal content**. Editors choose a new legal page or replace the currently selected legal draft, request review, inspect current/proposed compositions and SEO, and acknowledge the replacement before applying. New-page creation can still conflict with an existing route; select that existing legal record for replacement. Existing records, revisions and live content are protected by the backend workflow described above. The rest of page editing is disabled while a review or migration is pending, and unsaved page edits disable migration actions.

The browser verifies review hashes and target identity before displaying ready actions. Before sending an apply request it stores bounded account/website-scoped recovery identifiers, target revisions and source hashes, not source text. If storing these identifiers fails, no apply request is sent. Unknown outcomes retain the same request key; the panel supports status recovery and retrying that exact request, including after reload. Corrupt/mismatched recovery storage blocks further migration and directs the user to an administrator. No automatic clearing of an unconfirmed request occurs. Removing saved recovery data is only attempted after verified completion; a storage-clear failure leaves the request available for recovery.
