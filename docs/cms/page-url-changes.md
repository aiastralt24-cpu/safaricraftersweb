# Page URL changes and impact review

## Implemented locally

The page editor now offers **Review a page URL change** for an existing page. It accepts a proposed path and requests read-only evidence from `/api/cms/page-url-impact`. Migration 224 checks current view/edit permissions and the exact current revision. Existing path edits remain rejected by save/publication guards; this feature cannot change a URL or create a redirect.

Review distinguishes fixed website routes, invalid/reserved candidate paths, unchanged paths, occupied same-site/language paths and eligible candidates. Eligibility is not a reservation or permission to publish. Occupied records are not identified, avoiding disclosure of private content. Published targets with a different proposed path require a future redirect decision.

Impact scans current and published revisions separately. It reports local URLs in href, url, canonical and redirectPath fields, stripping query/fragment suffixes for exact path matching, plus structured recordId references. Results include self-references and references from other content types and languages in the same website. Only viewable source records appear. Pagination is UUID-ordered with 50 results per response; the target revision is rechecked on each request. Migration 225 also supplies an opaque impact snapshot covering target identity/current/published revisions, route occupancy and matching source revision identities, including restricted sources without returning their details. Pagination rejects changed snapshots in the client. The report remains live evidence; it does not authorize a route mutation.

The UI distinguishes draft/published links and identity references. Changing the proposed path clears previous results. Unsaved page edits disable review. The report explicitly states that restricted content, absolute URLs, free text, unsaved edits and external links require separate review; no-results is not a claim that the URL has no inbound links. A record-ID reference may continue resolving after a route change, whereas a literal URL may require updating or a redirect.

## Atomic application backend

Migration 229 and the authenticated proposal API `apply` action now apply an approved proposal as one database transaction. A private receipt binds the proposal, page, actor and transaction ID; the published-route guard permits only that exact transition while preserving the current MICE/private-aviation and other dedicated-route behavior. No content revision, language or publication pointer changes. Applied proposals are terminal and cannot be cancelled as if they were pending. Repeating the same proposal returns its applied status without repeating the transition or adding another job, even after subsequent moves.

Application requires current view/publish permission (including the site's privileged MFA policy), current reviewer membership/approval permission, separate-author requirements, unchanged page/revision/link-impact snapshot and available destination ownership. Activating MFA after the review requires a new approval proposal. For published pages, the current revision must already be published and approved, with an unexpired validation receipt matching the current validator policy. Newer unpublished edits must be resolved first. Draft-only pages stay unpublished and do not enqueue publication jobs.

The transaction changes the path, creates the old-address alias if requested, marks the proposal applied, records audit/receipt evidence and queues a publish delivery job for a live page. Existing older aliases continue to resolve directly to the page identity. Choosing no redirect creates no alias for the newly retired address; it does not delete earlier aliases. The delivery worker's full-layout invalidation covers both addresses. Database success means the job is queued, not that a remote cache refresh has finished.

Impact and ownership checks use short transaction table locks on records/redirects, plus membership/permission locks and the website row. This protects against intervening source writes/inserts during application but serializes these operations across websites. Hosted multi-connection contention/deadlock retry and load behavior still need verification; local PGlite tests cannot establish those properties.
