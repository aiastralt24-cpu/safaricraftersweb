# Global settings contract and impact review

Version 1 covers brand images/name, contact details/addresses, header variants and menu references, featured navigation content, CTA, footer link groups/legal/copyright/disclaimer/marks, social profiles, announcement/sticky CTA, cookie wording, default SEO/sharing, fallback image, search configuration and error/maintenance messages. Menus remain reusable navigation records; the settings contract does not flatten menu hierarchies into settings. Image references use the shared accessible-image contract. Arbitrary CSS/script/unknown fields and unsafe links are rejected. Defaults are a draft starting point, not an automatic migration from existing website code.

`globalSettingsImpact` compares validated settings without mutating them or producing noise from object key order. It reports potential shared scope and flags indexing/maintenance changes for elevated review. This is descriptive metadata, not authorization enforcement or a complete impacted-page inventory. Page overrides and actual live usage still require a dependency inventory.

`POST /api/cms/settings/review` accepts a candidate settings payload and existing record/revision identity. It reads the baseline through the user-authorized editor read, verifies type/identity/revision, validates both versions and returns impact only. Browser baselines, stale revisions and inaccessible records are rejected. It does not write settings or authorize publication.

Local migration 019 now enforces one settings record per website/locale and requires a null page path. It deliberately fails on duplicate/routed existing settings rather than deleting or merging data. Revision insertion requires explicit schema version, indexing mode and maintenance boolean; sensitive changes require current record-scoped configure permission in addition to ordinary draft permissions. Restore-as-draft uses the same checks. Approval/publication compare the candidate against the published baseline, so an intervening non-sensitive edit cannot remove the elevated authority requirement. These guards do not replace full schema validation, explicit impact acknowledgment, validation receipts or normal review/publish permissions.

Local migration 020 adds a locale-scoped settings workspace read under caller RLS, returning the permitted record and current create/configure capabilities. The GET settings API rejects unknown/duplicate parameters. The generic settings save endpoint now validates the full contract and requires a null page path. Direct DB writes retain their separate sensitive-field guards; full trusted publication validation is still pending.

The Settings workspace now exposes core branding/contact/footer/SEO/cookie/search text, header variants, sticky/language/search toggles and configuration-gated indexing/maintenance controls. Locale is entered explicitly. Structured fields not yet exposed remain in the cloned payload. Impact review is required by the form before saving; every edit clears it. Sensitive impact requires an explicit UI acknowledgment. This is not a database-bound acknowledgment receipt and is not a substitute for elevated publication permissions.

## Featured header content authoring

The structured settings editor now exposes an ordered collection of up to 12 featured journeys, destinations and journal articles. Editors search each supported content type through the existing authenticated reference API, add records, move them across the combined order and remove them. Duplicate selections are rejected with visible feedback. Selected records resolve across supported types; unresolved or inaccessible references retain their IDs for repair instead of silently disappearing. Published-revision labels do not assert public eligibility: existing saved settings validation still checks current type, language and dependency evidence.

These edits use the parent settings draft flow, invalidating impact review and requiring review before save. Busy/read-only states disable controls. No publication policy or rollout flag changed. This supersedes earlier notes that featured-content editing is missing; settings publication and provider acceptance remain pending.
