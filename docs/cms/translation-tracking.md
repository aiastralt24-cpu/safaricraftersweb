## Behavior

- Creating a translation copies one exact current primary-source revision into a new locale draft. It does not translate the text, approve it or publish it. Only one translation per source and locale is allowed; translation chains are rejected.
- Creation requires source visibility and permission to create the content type. The caller supplies an immutable request key. Retrying the same request returns its original record/revision receipt even after later edits; changing its parameters is rejected. The future client must persist this request before sending it.
- Status requires visibility of both records. It distinguishes `unreviewed`, `source_changed`, `translation_changed` and `current`. Source-change status takes precedence when both sides changed.
- Translation review acknowledges exact current source and target revisions. It requires approval permission and a separate reviewer when the website requires separation. It does not substitute for normal approval or trusted validation.
- Publication of a new translated revision is blocked until its translation review matches both the proposed revision and the current source revision. Existing publication guards remain in force. Source edits mark a translation review-due; they do not automatically withdraw previously published content.
- Relationships and receipts are private. Authenticated callers use permission-checking RPCs; direct table access and anonymous calls are denied. Audit events record creation and review. The HTTP endpoint uses caller credentials and private, non-cacheable responses.

## Recoverable creation and cancellation

`lib/cms/translation-creation.ts` persists a bounded, account/site/source-scoped request before transport. It stores no content or credentials. Web Locks serialize cooperating tabs. Recovery sends the original source revision, locale, path and request key; it never silently replaces an unresolved request with current editor fields. Creation responses carry the site and request key. Verified receipts remain stored until the returned draft has loaded successfully. In-memory attempted-request identities protect delayed calls after another tab clears shared storage.

Migration 243 adds cancellation tombstones under the same transaction advisory lock used by creation. Cancelling an already committed request returns its original draft receipt without deleting the record. Cancelling an uncommitted request prevents any later create using that identity. Cancellation retries are idempotent; changed parameters are rejected. The earlier unfenced creation function is private and no longer executable by authenticated users. Cancellation data is also private. There is no local-only discard or automatic expiry of ambiguous requests.

Local database tests verify cancel-before-create, create-before-cancel, repeated cancellation, changed manifests, anonymous/outsider denial, raw-table denial and denial of the unfenced function.
